Setup & Configuration

01
Before using Git, set up your identity. This information is embedded in every commit you make, so collaborators know who made each change.
git config Configure Git settings
Sets your name, email, and other preferences. The --global flag applies settings to all repositories on your machine.
terminal 
# Set your name and email (required — done once)
git config --global user.name "Your Name"
git config --global user.email "you@example.com"

# Set your default branch name to 'main'
git config --global init.defaultBranch main

# Set your preferred editor (e.g. VS Code)
git config --global core.editor "code --wait"

# View all current settings
git config --list
💡
Tip: Use --global for personal settings and omit it (or use --local) to configure only the current repository.
🚀

Init & Clone

02
Every Git project starts with either initializing a fresh repo or cloning an existing one. These are the entry points to version control.
git init Initialize a new repository
Creates a new, empty Git repository in the current directory. This creates a hidden .git/ folder that tracks all your version history.
terminal
# Initialize repo in the current directory
git init

# Initialize a new repo in a named folder
git init my-project

# Output: Initialized empty Git repository in /path/to/my-project/.git/
git clone Copy a remote repository locally
Downloads a complete copy of an existing repository — including all branches, commits, and history — to your local machine. This is how you start working on an existing project.
terminal
# Clone a repo into a new folder (folder name = repo name)
git clone https://github.com/user/repo.git

# Clone into a specific folder name
git clone https://github.com/user/repo.git my-folder

# Clone only the latest snapshot (faster, less history)
git clone --depth 1 https://github.com/user/repo.git

# Clone a specific branch
git clone --branch develop https://github.com/user/repo.git
Remote Repo (GitHub)
→
git clone
→
Local Repo (your machine)

Status & Diff

03
Before staging or committing, always check what's changed. These commands give you a clear picture of your working directory.
git status See what's changed
Shows which files are modified, staged, or untracked. Run this constantly — it's your GPS in a repository.
terminal
git status

On branch main
Your branch is up to date with 'origin/main'.

Changes to be committed (staged):
  new file:   src/app.js

Changes not staged for commit (modified):
  modified:   README.md

Untracked files (not tracked by git):
  config.local.json

# Short/compact output
git status -s
git diff View line-by-line changes
Shows the exact lines that changed. Red lines (−) were removed, green lines (+) were added.
terminal
# Show unstaged changes (working directory vs last commit)
git diff

# Show staged changes (what you're about to commit)
git diff --staged

# Compare two branches
git diff main..feature-login

# Compare a specific file only
git diff README.md
📦

Staging Files

04
The staging area (also called the "index") is a preparation zone. You choose exactly which changes to include in your next commit — giving you precise control over your history. 
  Working Directory   →   Staging Area (Index)   →   Repository
  (your edits)            (git add)                  (git commit)
git add Stage changes for commit
Moves changes from your working directory to the staging area, marking them to be included in the next commit.
terminal
# Stage a specific file
git add index.html

# Stage all changed files in the current directory
git add .

# Stage all .js files
git add *.js

# Stage parts of a file interactively (choose hunks)
git add -p app.js

# Unstage a file (undo git add)
git restore --staged index.html
⚠️
Caution: git add . stages everything including unintended files. Use a .gitignore file to exclude files like node_modules/, .env, and build outputs.
✅

Committing Changes

05
A commit is a permanent snapshot saved to your repository's history. Good commits are small, focused, and have clear messages explaining why the change was made.
git commit Save staged changes to history
Takes everything in the staging area and saves it as a permanent commit with a unique ID (SHA hash) in your repository's history.
terminal
# Standard commit with a message
git commit -m "feat: add user login form"

# Stage all tracked files AND commit in one step
git commit -am "fix: correct typo in header"

# Amend the last commit (message or files)
git commit --amend -m "feat: add user login form with validation"

# Amend without changing the message
git commit --amend --no-edit
💡
Conventional Commits: A popular format is type: description. Common types: feat (new feature), fix (bug fix), docs (documentation), chore (maintenance), refactor (code restructure).
⚠️
Never amend a commit that has already been pushed to a shared remote branch — it rewrites history and causes problems for teammates.
📜

History & Log

06
View your commit history, search through past changes, and understand who changed what and when.
git log Browse commit history
Displays the list of all commits in the current branch, most recent first. Highly customizable with flags.
terminal
# Default log view (author, date, message)
git log

# Compact one-line view
git log --oneline

# Graphical branch tree view
git log --oneline --graph --all --decorate

# Show last 5 commits only
git log -5

# Search commits by message keyword
git log --grep="login"

# Show commits by a specific author
git log --author="Alice"

# Show what changed in each commit
git log -p


# Example output (--oneline):
a3f9b21 feat: add user authentication
c801de5 fix: resolve null pointer on login
9f2a114 docs: update README with setup steps
📡

Fetch

07
Fetch downloads changes from the remote without modifying your local working directory. It's the safest way to "look before you leap".
git fetch Download remote changes safely safe
Downloads commits, branches, and tags from the remote repository to your remote-tracking branches (e.g., origin/main). Your local branches are not changed — you inspect first, then decide to merge.
terminal
# Fetch from the default remote (origin)
git fetch

# Fetch from a specific remote
git fetch origin

# Fetch a specific branch
git fetch origin feature-auth

# Fetch all remotes at once
git fetch --all

# After fetch: view what changed vs your local main
git log main..origin/main --oneline
Remote (origin/main)
→
git fetch
→
origin/main (local copy)
→
Your local main (unchanged)
ℹ️
fetch vs pull: git fetch only downloads — it never touches your working files. git pull = git fetch + git merge. Use fetch when you want to review changes before integrating.
⬇️

Pull

08
git pull Fetch and integrate remote changes
Fetches remote changes AND immediately integrates them into your current branch. Equivalent to running git fetch followed by git merge.
terminal
# Pull from the tracked remote branch
git pull

# Pull from a specific remote and branch
git pull origin main

# Pull and rebase instead of merge (cleaner history)
git pull --rebase

# Always use rebase when pulling (set as default)
git config --global pull.rebase true
💡
Best Practice: Many teams prefer git pull --rebase to keep a linear, cleaner commit history without auto-generated merge commits.
⬆️

Push

09
git push Upload local commits to remote
Sends your committed local changes to a remote repository (like GitHub or GitLab), making your work available to teammates.
terminal
# Push current branch to origin
git push

# Push and set the upstream tracking branch
git push -u origin feature-login

# Push a specific branch
git push origin feature-login

# Push all local branches
git push --all

# Push tags
git push --tags

# Delete a remote branch
git push origin --delete old-branch
⚠️
Force Push Warning: git push --force overwrites remote history and is dangerous on shared branches. Use git push --force-with-lease as a safer alternative — it only force-pushes if nobody else has pushed since you last fetched.
FlagDescription
-u / --set-upstreamLinks your local branch to the remote branch (only needed once)
--forceOverwrites remote history ⚠️ Use with extreme caution
--force-with-leaseSafer force push — fails if others have pushed
--tagsPushes all local tags to remote
--deleteDeletes a remote branch
🌐

Remote Management

10
git remote Manage remote connections
Remotes are named links to external repositories. The default remote created by git clone is always called origin.
terminal
# List all remotes
git remote -v

# Add a new remote
git remote add origin https://github.com/user/repo.git

# Change the URL of an existing remote
git remote set-url origin https://github.com/user/new-repo.git

# Remove a remote
git remote remove origin

# Show detailed info about a remote
git remote show origin
🌿

Branching

11
Branches allow you to develop features, fix bugs, or experiment in an isolated environment. The main branch is your stable production code; everything else is work-in-progress. 
  main    ──●──────────────────────────●── (merge)
             \                        /
  feature     ●──●──●──●──●──●──●──●
                  (feature branch)
git branch List, create, and delete branches
terminal
# List all local branches (* marks the current branch)
git branch

# List all branches including remote-tracking
git branch -a

# Create a new branch (stays on current branch)
git branch feature-navbar

# Delete a merged branch safely
git branch -d feature-navbar

# Force delete an unmerged branch
git branch -D feature-navbar

# Rename the current branch
git branch -m new-name
🔀

Checkout & Switch

12
git checkout Switch branches or restore files
Switches your working directory to a different branch. Modern Git recommends using the newer git switch for branch switching and git restore for file operations.
terminal
# Switch to an existing branch
git checkout main

# Create AND switch to a new branch (most common!)
git checkout -b feature-signup

# Modern equivalent (Git 2.23+)
git switch main
git switch -c feature-signup

# Discard changes in a file (restore from last commit)
git checkout -- index.html
# Modern equivalent:
git restore index.html

# Checkout a remote branch as a local tracking branch
git checkout -b feature-auth origin/feature-auth
🔗

Merging

13
Merging combines the changes from one branch into another. It's how completed features make their way into the main codebase.
git merge Integrate branches together
Merges the specified branch into your currently active branch. Git uses two strategies: a fast-forward (no new commit) when possible, or a merge commit when the branches have diverged.
terminal
# Merge a feature branch into main (first switch to main)
git checkout main
git merge feature-login

# Always create a merge commit (no fast-forward)
git merge --no-ff feature-login

# Squash all feature commits into one (clean history)
git merge --squash feature-login
git commit -m "feat: implement user login"

# Abort a merge in progress (if conflicts arise)
git merge --abort
  FAST-FORWARD MERGE (no divergence):
  main     ──●──●
                  \
  feature          ●──●──●
  After merge → main: ──●──●──●──●──●

  THREE-WAY MERGE (branches diverged):
  main     ──●──●──────────────────●M (merge commit)
               \                  /
  feature       ●──●──●──●──●──●
Handling Merge Conflicts: When Git can't automatically combine changes, it marks the conflicting sections. You must resolve them manually.
resolving conflicts
# After a conflict, Git marks the file like this:
<<<<<<< HEAD
  const greeting = "Hello World";  ← your version
=======
  const greeting = "Hi there!";    ← incoming version
>>>>>>> feature-login

# Step 1: Edit the file and decide which version to keep
# Step 2: Stage the resolved file
git add src/app.js

# Step 3: Complete the merge
git commit

# Or use a visual merge tool
git mergetool
↩️

Rebase

14
Rebase rewrites your commit history by replaying commits on top of another base. It produces a cleaner, linear history compared to merging — but rewrites commits, so use with care on shared branches.
git rebase Replay commits on a new base rewrites history 
  MERGE result (fork in history):
  main     ──●──●──────────────────●M
               \                  /
  feature       ●──A──B──C──D──●

  REBASE result (linear history):
  main     ──●──●──●──A'─B'─C'─D'
               (feature commits replayed on top of main)
terminal
# Rebase your feature branch onto main
git checkout feature-login
git rebase main

# Interactive rebase: edit, squash, reorder last 3 commits
git rebase -i HEAD~3

# Continue after resolving a conflict during rebase
git rebase --continue

# Skip the current conflicting commit
git rebase --skip

# Abort and return to the original state
git rebase --abort
Interactive Rebase Actions:
ActionWhat It Does
pickKeep the commit as-is
rewordKeep the commit but edit its message
editKeep the commit but pause to amend it
squashMerge this commit into the previous one (keep both messages)
fixupMerge into previous commit, discard this commit's message
dropCompletely remove this commit from history
⚠️
Golden Rule of Rebase: Never rebase a branch that others are working on. Rebase rewrites commit hashes — if teammates have based work on your old commits, they'll get conflicts. Only rebase commits that exist only on your local machine.
💡
Rebase Merge Strategy: Many teams use a "rebase then merge" workflow: rebase your feature onto main to get a clean history, then fast-forward merge into main. This gives you a perfectly linear commit history with no merge commits.
📌

Stash

15
Stash temporarily saves your uncommitted changes so you can switch contexts (e.g., fix a bug on another branch) and come back later.
git stash Temporarily shelve your work
terminal
# Save current uncommitted changes to the stash
git stash

# Stash with a descriptive name
git stash push -m "WIP: half-built navbar"

# List all stashes
git stash list
stash@{0}: WIP: half-built navbar
stash@{1}: On main: quick fix attempt

# Apply the latest stash (keep it in the stash list)
git stash apply

# Apply AND remove from stash list
git stash pop

# Apply a specific stash by index
git stash apply stash@{1}

# Delete a specific stash
git stash drop stash@{0}

# Delete ALL stashes
git stash clear

# Stash including untracked files
git stash -u
🏷️

Tags

16
Tags mark specific commits as important milestones — typically software releases (v1.0.0, v2.3.1). Unlike branches, tags don't move when new commits are added.
git tag Mark release points in history
terminal
# List all tags
git tag

# Create a lightweight tag (simple pointer)
git tag v1.0.0

# Create an annotated tag (recommended — includes message)
git tag -a v1.0.0 -m "Initial stable release"

# Tag a specific past commit
git tag -a v0.9.0 9f2a114 -m "Beta release"

# Push a tag to remote
git push origin v1.0.0

# Push all tags at once
git push --tags

# Delete a local tag
git tag -d v1.0.0

# Delete a remote tag
git push origin --delete v1.0.0
ℹ️
Semantic Versioning: Follow the MAJOR.MINOR.PATCH pattern. Example: v2.1.3 = major version 2, minor update 1, patch 3. A breaking change increments MAJOR, a new feature increments MINOR, a bug fix increments PATCH.
⏪

Reset, Revert & Undo

17
Mistakes happen. Git gives you several ways to undo changes, each with different levels of impact on your history. Choose carefully.
git reset Move HEAD and optionally unstage/discard caution
Moves the current branch HEAD to a previous commit. The --soft, --mixed, and --hard flags control what happens to your working directory and staging area.
terminal
# --soft: Move HEAD back, keep changes staged
git reset --soft HEAD~1

# --mixed (default): Move HEAD back, unstage changes, keep files
git reset HEAD~1

# --hard: Move HEAD back, DISCARD all changes permanently ⚠️
git reset --hard HEAD~1

# Reset to a specific commit hash
git reset --hard a3f9b21
ModeHEAD Moves?Staging AreaWorking Files
--soft✅ YesUnchanged (changes staged)Unchanged
--mixed✅ YesCleared (unstaged)Unchanged
--hard✅ YesCleared⚠️ Discarded permanently
git revert Safely undo a commit safe for shared branches
Creates a new commit that undoes the changes of a previous commit. Unlike reset, it doesn't rewrite history — it's safe to use on shared/public branches.
terminal
# Revert the last commit (creates a new "undo" commit)
git revert HEAD

# Revert a specific commit by hash
git revert a3f9b21

# Revert without opening the commit message editor
git revert HEAD --no-edit

# Revert multiple commits as one revert commit
git revert HEAD~3..HEAD
💡
Reset vs Revert: Use git reset for local-only cleanup before pushing. Use git revert when you need to undo a commit on a shared branch without disrupting teammates' history.
git restore Discard file changes
The modern way to discard changes in your working directory or unstage files. Introduced in Git 2.23 as a clearer alternative to git checkout --.
terminal
# Discard changes in a file (restore from last commit)
git restore index.html

# Discard ALL uncommitted changes in working directory ⚠️
git restore .

# Unstage a file (remove from staging area, keep changes)
git restore --staged index.html
⚡
